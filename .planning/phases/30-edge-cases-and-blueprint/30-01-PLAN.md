<interfaces>
Key contracts for this docs-only phase:

From `30-CONTEXT.md`:
- D-01: Use a representative edge-case suite covering mixed geometry types, stacked `geom_sf`, and faceted sf maps.
- D-02: First build supports polygon-family geometries only: `POLYGON` and `MULTIPOLYGON`.
- D-03: Stacked `geom_sf` layers in one panel share one panel projection/bbox.
- D-04: Faceted sf maps prioritize per-panel projection from each panel's data.
- D-05: The final document is a build-phase roadmap.
- D-06: The blueprint includes a concrete file-by-file checklist.
- D-07: First future build phase is a production-safe MVP: single-panel polygon choropleths with tooltip, hover, centroid brush, and zoom suppression.
- D-08: Validation mixes R tests, JavaScript checks, and visual/browser comparisons.
- D-09: Include at least five anti-features: tile basemaps, slippy zoom/pan, JavaScript-side reprojection, polygon-overlap brushing, and large-map performance guarantees.
- D-10: Anti-features are first-build deferrals with rationale and revisit conditions.
- D-11: Tile basemaps and slippy controls are out of scope because gg2d3 is an SVG/htmlwidgets renderer focused on ggplot parity.
- D-12: Large-map performance is limited/deferred.
- D-13: Lightweight probes/check commands are allowed, but the written blueprint is primary.
- D-14: Faceted sf validation is IR/DOM contract evidence around `PANEL`, panel bbox/projection behavior, and future tests.
- D-15: Mixed geometry validation includes unsupported-case test planning.
- D-16: Leave no unresolved implementation choices.

From `30-RESEARCH.md`:
- Current `sf.js` computes projection per layer, so stacked layers need shared panel projection state.
- Current `as_d3_ir.R` preserves `PANEL` and computes global sf bbox, so faceted sf work needs explicit per-panel bbox/projection semantics.
- Future implementation should start with a polygon MVP and defer non-polygon rendering.
- Source files are future implementation hooks and must not be edited in this phase.
