# Phase 31: pkgdown and GH Pages publishing - Research

**Researched:** 2026-05-15
**Domain:** R package documentation site (pkgdown 2.2.0) + GitHub Pages deployment via r-lib GHA + htmlwidgets interactivity preservation
**Confidence:** HIGH (workflow + pkgdown idioms verified live); MEDIUM (htmlwidgets-in-pkgdown failure modes — verified general behavior; gg2d3-specific failure modes will surface only on first local build per D-12).

## Summary

The phase publishes a pkgdown site from already-finished v1.1 docs to `https://davidzenz.github.io/gg2d3/`. The mechanics are well-trodden: r-lib's `pkgdown.yaml` GHA workflow (verified at `r-lib/actions@v2-branch` on 2026-05-15) calls `pkgdown::build_site_github_pages()` and pushes `docs/` to a `gh-pages` branch via `JamesIves/github-pages-deploy-action@v4.8.0`. The workflow needs `permissions: contents: write`; it does **not** create the `gh-pages` branch — that bootstrap is `usethis::use_pkgdown_github_pages()`'s responsibility (or a one-shot manual orphan-branch push).

Two real risks dominate this phase, both flagged by CONTEXT D-09 and D-14/D-15:

1. **"Get started" promotion is filename-based, not YAML-based** in pkgdown 2.x. A vignette named `vignettes/<package>.Rmd` (here: `gg2d3.Rmd`) is auto-promoted to the navbar's "Get started" slot. The current intro vignette is `gg2d3-intro.Rmd` — it will NOT be promoted unless renamed (or symlinked, or its `articles:` index entry is added with a `getting-started` flag in the YAML — but the canonical 2.x idiom is the rename). Planner must decide: rename `gg2d3-intro.Rmd` → `gg2d3.Rmd` (cleanest) or add an `articles:` block.

2. **htmlwidgets in pkgdown articles are not guaranteed to remain interactive.** pkgdown's own jQuery/Bootstrap take precedence over a widget's dependencies, and the `<name>_files/` asset directory must survive the build copy. The vendored `inst/htmlwidgets/lib/d3/d3.v7.min.js` is bundled by `htmlwidgets::createWidget()` as a widget dependency — pkgdown should copy it into `docs/articles/<vignette>_files/`. Failure modes (script-stripping, missing `_files/`, asset path rewrite gone wrong) are real but rare; D-15 mandates a dedicated local-verification wave before committing the workflow.

**Primary recommendation:** Rename `vignettes/gg2d3-intro.Rmd` → `vignettes/gg2d3.Rmd` for clean auto-promotion (also updates the `%\VignetteIndexEntry{}` line). Build the site locally with `pkgdown::build_site_github_pages()` (not just `build_site()`), open `docs/articles/gg2d3.html` in a browser, confirm a `<script>` block referencing `d3.v7.min.js` is present and zoom/tooltip work. Only after that human-verified local check, commit `.github/workflows/pkgdown.yaml`, push, and follow up with the D-14 published-site checkpoint.

### Pattern 1: r-lib pkgdown.yaml workflow (CANONICAL — paste verbatim)

**What:** The full r-lib `pkgdown.yaml` workflow, fetched live from `r-lib/actions@v2-branch/examples/pkgdown.yaml` on 2026-05-15.
**When to use:** Always. D-01 mandates this exact workflow.
**Example:**
```yaml
# Source: https://github.com/r-lib/actions/blob/v2-branch/examples/pkgdown.yaml (fetched 2026-05-15)
# Workflow derived from https://github.com/r-lib/actions/tree/v2/examples
# Need help debugging build failures? Start at https://github.com/r-lib/actions#where-to-find-help
on:
  push:
    branches: [main, master]
  pull_request:
  release:
    types: [published]
  workflow_dispatch:

name: pkgdown.yaml

permissions: read-all

jobs:
  pkgdown:
    runs-on: ubuntu-latest
    concurrency:
      group: pkgdown-${{ github.event_name != 'pull_request' || github.run_id }}
    env:
      GITHUB_PAT: ${{ secrets.GITHUB_TOKEN }}
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v6

      - uses: r-lib/actions/setup-pandoc@v2

      - uses: r-lib/actions/setup-r@v2

      - uses: r-lib/actions/setup-r-dependencies@v2
        with:
          extra-packages: any::pkgdown, local::.
          needs: website

      - name: Build site
        run: pkgdown::build_site_github_pages(new_process = FALSE, install = FALSE)
        shell: Rscript {0}

      - name: Deploy to GitHub pages 🚀
        if: github.event_name != 'pull_request'
        uses: JamesIves/github-pages-deploy-action@d92aa235d04922e8f08b40ce78cc5442fcfbfa2f # v4.8.0
        with:
          clean: false
          branch: gh-pages
          folder: docs
```

**Notes on this file:**
- `permissions: read-all` at workflow scope + `contents: write` at job scope = principle of least privilege; sufficient for pushing to `gh-pages`.
- Build uses `pkgdown::build_site_github_pages()` (NOT `build_site()` — there's a difference: `build_site_github_pages()` adds a `.nojekyll` file so GitHub Pages doesn't try to Jekyll-process the output, which would mangle `_files/` directories). **CONTEXT D-01 says `build_site()`/`deploy_to_branch()`; the live r-lib template uses `build_site_github_pages()` + `JamesIves` action. The live template is the authoritative source per D-01's "the one generated by `usethis::use_pkgdown_github_pages()`."** Planner: use the live template verbatim.
- `pull_request` trigger fires the build but the `if: github.event_name != 'pull_request'` guard skips deploy → CONTEXT D-02 ("no PR previews") is honored: PRs build but don't deploy. This is acceptable PR-validation, not a "preview deploy."
- `actions/checkout@v6` is the current major. SHA-pinning of `JamesIves` is preserved verbatim from r-lib.

### Pattern 2: "Get started" auto-promotion via filename

**What:** In pkgdown 2.x, a vignette named exactly `vignettes/<pkgname>.Rmd` (or `vignettes/articles/<pkgname>.Rmd`) is automatically promoted to the navbar as a standalone "Get started" link. No `_pkgdown.yml` `articles:` block is needed.
**When to use:** This is the canonical idiom for the D-09 promotion.
**Example (recommended path):**
```bash
git mv vignettes/gg2d3-intro.Rmd vignettes/gg2d3.Rmd
```
And inside the file, update the VignetteIndexEntry to keep `R CMD check` happy:
```yaml
---
title: "Getting started with gg2d3"
output: rmarkdown::html_vignette
vignette: >
  %\VignetteIndexEntry{Getting started with gg2d3}
  %\VignetteEngine{knitr::rmarkdown}
  %\VignetteEncoding{UTF-8}
---
```
The `VignetteIndexEntry` content is human-readable and does NOT need to match the filename; only the filename triggers pkgdown's auto-promotion.
[VERIFIED: pkgdown.r-lib.org/reference/build_articles.html — "a vignette with the same name as the package... automatically becomes a top-level 'Get started' link"]

**Alternative (NOT recommended):** Keep `gg2d3-intro.Rmd` and add an `articles:` index entry. This worked in older pkgdown versions via various flags; current 2.x docs do not document a stable YAML-only path. The rename is the future-proof choice.

### Anti-Patterns to Avoid

- **`output: html_document` with `as_is: true`** — explicitly documented to break htmlwidgets in pkgdown. The vignettes use `rmarkdown::html_vignette`; do not change this.
- **`pkgdown::build_site()` over `pkgdown::build_site_github_pages()` in CI** — the latter adds the critical `.nojekyll` file. Use the r-lib template verbatim.
- **Custom `navbar:` block** — D-06 forbids; defaults are right.
- **Hand-editing `README.md` to fix anything pkgdown-related** — README is `.Rmd`-generated (CLAUDE.md rule). If a homepage tweak is needed, edit `README.Rmd` and rebuild.
- **Manually copying `d3.v7.min.js` into `docs/`** — htmlwidgets dependency system handles this. If it doesn't end up there after a build, the fix is upstream (chunk option, widget config), not a postprocess copy.
- **Deferring the local build verification (D-15) to CI** — first failure on CI = embarrassing public broken site. Local `pkgdown::build_site_github_pages()` + browser inspect is mandatory pre-commit.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTML doc site from R package | Custom Rmd → HTML pipeline | `pkgdown::build_site_github_pages()` | Handles roxygen Rd→HTML, navbar, search, theming, NEWS, vignettes, link-resolution |
| GH Pages deploy from `docs/` | Hand-rolled `git push gh-pages` step | `JamesIves/github-pages-deploy-action@v4.8.0` (SHA-pinned in r-lib template) | Handles orphan-branch rebase, `.nojekyll`, force-push semantics correctly |
| gh-pages branch bootstrap | Read & implement git plumbing | `usethis::use_pkgdown_github_pages()` (one R command) | Creates orphan branch, configures Pages settings, sets URL in `_pkgdown.yml` + DESCRIPTION, installs the workflow file |
| htmlwidget JS asset bundling | `file.copy()` of `d3.v7.min.js` to `docs/articles/` | `htmlwidgets::createWidget()` dep system | Already wired; pkgdown reads htmlwidget deps and copies them automatically |
| "Get started" navbar slot | Custom `_pkgdown.yml` `navbar:` block | Rename vignette to `<pkgname>.Rmd` | Filename convention is the documented 2.x mechanism |

**Key insight:** Phase 31 is 90% configuration, 10% verification. There is no R code to write. The win condition is "things the ecosystem already provides, wired correctly."

## Common Pitfalls

### Pitfall 1: vignette rename breaks internal cross-references
**What goes wrong:** After `git mv gg2d3-intro.Rmd gg2d3.Rmd`, README/NEWS/other vignettes that link `articles/gg2d3-intro.html` 404 in the built site.
**Why it happens:** pkgdown derives output article HTML filenames from source `.Rmd` filenames.
**How to avoid:** `grep -rn "gg2d3-intro" .` before committing the rename; update every hit (link text in README.Rmd, any `[See the intro](...)` references in the other vignette, etc.). Then `devtools::build_readme()` if `README.Rmd` changed.
**Warning signs:** Broken-link warnings during `pkgdown::build_site_github_pages()` (it prints them). Browser 404s during the D-15 local check.

### Pitfall 2: `.github/` not in `.Rbuildignore` → CRAN check NOTE/WARNING
**What goes wrong:** `R CMD check --as-cran` flags `.github/workflows/pkgdown.yaml` as "non-standard top-level files" or includes it in the source tarball.
**Why it happens:** Default `.Rbuildignore` doesn't cover `.github/`; Phase 17 added other entries but the directory didn't exist then. Current `.Rbuildignore` lacks `^\.github$` (VERIFIED 2026-05-15).
**How to avoid:** Add `^\.github$` to `.Rbuildignore` in the same commit that creates `.github/workflows/pkgdown.yaml`. Existing entries that are still relevant: `^docs$` (present), `^pkgdown$` (present), `^_pkgdown\.yml$` (present).
**Warning signs:** `devtools::check()` from a clean session reports new NOTEs about `.github`. Phase 17's `R CMD check` was clean — any new NOTE in Phase 31 is from this miss.

### Pitfall 3: First workflow run fails because `gh-pages` branch doesn't exist
**What goes wrong:** `JamesIves/github-pages-deploy-action` can create the branch on first run BUT requires the `clean: false` setting (which the r-lib template includes) AND that the repo's Pages settings already point to `gh-pages`. If Pages is set to `main` or unconfigured, the first deploy "succeeds" but the site never serves.
**Why it happens:** Two separate configurations (branch existence + Pages source setting) and the workflow only addresses the first.
**How to avoid:** Either (a) run `usethis::use_pkgdown_github_pages()` once locally — it handles branch creation AND repo settings AND adds the workflow file AND patches `_pkgdown.yml` URL AND DESCRIPTION URL all in one shot — OR (b) manually:
```bash
# Create the orphan branch
git checkout --orphan gh-pages
git rm -rf .
echo "placeholder" > index.html
git add index.html
git commit -m "Initial gh-pages"
git push origin gh-pages
git checkout master
# Then go to github.com/DavidZenz/gg2d3/settings/pages
# Source: "Deploy from a branch"
# Branch: gh-pages / (root)
# Save
```
**Recommendation:** Use `usethis::use_pkgdown_github_pages()` — it's idempotent and documents all side-effects upfront. Run from a fresh R session at the repo root. If usethis tries to overwrite the `_pkgdown.yml` stub or modify the workflow in ways that conflict with D-NN, manually reconcile. Plan should include a verification step: after usethis runs, `git diff` to confirm exactly which files changed.
**Warning signs:** First workflow run completes but `https://davidzenz.github.io/gg2d3/` shows 404 or "Pages not configured."

### Pitfall 4: htmlwidgets render as a static <div> instead of interactive widget
**What goes wrong:** Published article shows an empty box, a static SVG, or a "broken widget" placeholder.
**Why it happens (failure modes, ordered by likelihood):**
1. **GitHub Pages Jekyll-processed the `_files/` directory** — Jekyll skips directories starting with `_`. `build_site_github_pages()` adds `.nojekyll` at the docs root to disable Jekyll. If `.nojekyll` is missing, asset directories vanish.
2. **`screenshot.force = TRUE`** somewhere in `_pkgdown.yml` or chunk options — pkgdown replaces the widget with a webshot screenshot. Defaults to FALSE in modern pkgdown; check `_pkgdown.yml` doesn't override.
3. **`d3.v7.min.js` not registered as an htmlwidget dependency** — verify the widget's R-side `createWidget()` call uses `htmltools::htmlDependency()` (or `htmlwidgets.yaml`'s `dependencies:` block) to bundle the JS. (Current implementation: `inst/htmlwidgets/gg2d3.yaml` declares the dep — VERIFIED earlier in project history.)
4. **pkgdown's jQuery/Bootstrap conflict with widget's bundled jQuery/Bootstrap** — pkgdown docs note its versions "take precedence." Usually harmless; can break widgets that depend on a specific jQuery version. gg2d3 doesn't use jQuery, so this is N/A.
5. **Chunk emits a widget but knitr captures stdout instead of the widget object** — fix with `htmltools::tagList(gg2d3(...))` as the chunk's last expression. CONTEXT D-15 mentions this fix.
**How to avoid:** Run `pkgdown::build_site_github_pages()` locally → open `docs/articles/gg2d3.html` in Chrome → DevTools → confirm: (a) `.nojekyll` file exists at `docs/`, (b) the article HTML contains `<script src="...d3.v7.min.js">`, (c) the article HTML contains a `<div class="...html-widget...">`, (d) console shows no JS errors, (e) clicking/scrolling on the widget actually does things. Only after all five pass: commit the workflow.
**Warning signs:** Empty div in published site; console errors `d3 is not defined`; `_files/` directory missing from GH Pages even though local `docs/articles/` has it.

### Pitfall 5: CONTEXT D-01 mentions `pkgdown::deploy_to_branch()`, r-lib template uses different mechanism
**What goes wrong:** Planner takes D-01 literally and tries to use `pkgdown::deploy_to_branch()` (an R function) as the deploy step, instead of the `JamesIves` GHA action that the r-lib template actually uses.
**Why it happens:** D-01's wording is shorthand; "the workflow generated by `usethis::use_pkgdown_github_pages()`" is the binding spec, and that workflow is exactly the YAML in Pattern 1 above. `pkgdown::deploy_to_branch()` is a separate R-side helper for local-deploy workflows, not used in the CI template.
**How to avoid:** Trust the live r-lib template (Pattern 1). The intent of D-01 is "use the standard r-lib path," not "literally call deploy_to_branch in CI."
**Warning signs:** Planner writes a custom workflow step calling `Rscript -e 'pkgdown::deploy_to_branch()'` instead of using the `JamesIves` action.

### Pitfall 6: `actions/checkout@v6` permissions vs. push-to-gh-pages
**What goes wrong:** Deploy step fails with "Resource not accessible by integration."
**Why it happens:** Job-level `permissions: contents: write` is required. Workflow-level `permissions: read-all` alone is insufficient. The r-lib template sets both — preserve verbatim.
**How to avoid:** Don't strip the `permissions:` blocks from the workflow. They look redundant but aren't.
**Warning signs:** First workflow run fails with a 403 at the deploy step.
