# Phase 31: pkgdown and GH Pages publishing - Context

**Gathered:** 2026-05-15
**Status:** Ready for planning

<domain>
## Phase Boundary

A pkgdown site is built from the v1.1 documentation (`README.md`, `vignettes/gg2d3-intro.Rmd`, `vignettes/gg2d3-interactivity.Rmd`, roxygen reference, `NEWS.md`) and published to GitHub Pages at `https://davidzenz.github.io/gg2d3/` via a standard r-lib GitHub Actions workflow. The phase is complete when:

1. A user visiting the published URL sees an up-to-date pkgdown site reflecting current `master`.
2. At least one `gg2d3()` widget in the published "Get started" article is **interactively rendered** (not a static screenshot) — confirming htmlwidgets + the vendored `d3.v7.min.js` survive the pkgdown build.
3. Subsequent pushes to `master` (and tagged releases) refresh the published site automatically with no manual steps.

Scope is **publishing infrastructure only**: pkgdown config, GHA workflow, gh-pages deploy, post-deploy widget verification. No documentation content rewrites — the README and vignettes from Phase 18 are inputs, not editable artifacts. R CMD check on CI is explicitly NOT part of this phase.

</domain>

<decisions>
## Implementation Decisions

### Deploy mechanism & site URL
- **D-01:** Use the standard r-lib `pkgdown.yaml` GitHub Actions workflow (the one generated by `usethis::use_pkgdown_github_pages()`). Build runs `pkgdown::build_site()` and deploys to the `gh-pages` branch via `pkgdown::deploy_to_branch()`. No `peaceiris/actions-gh-pages`, no manual local-only deploys.
- **D-02:** Workflow triggers on **push to `master`** and on **`release` events** (matches r-lib default). No PR previews in this phase. No `workflow_dispatch`-only mode.
- **D-03:** Canonical site URL is `https://davidzenz.github.io/gg2d3/`. Set as `url:` in `_pkgdown.yml`. This also aligns with `DESCRIPTION`'s `URL:` field (which currently points to the GitHub repo; the planner may add the pkgdown URL alongside it).
- **D-04:** Phase 31 deploys pkgdown **only**. R CMD check matrix on CI is deferred to a future phase (see Deferred Ideas). The workflow file added in this phase should be `pkgdown.yaml` and contain a single `pkgdown` job — no `check-r-package` matrix.

### Navbar & reference structure
- **D-05:** `_pkgdown.yml` `reference:` is **curated**, not default-alphabetical. Sections:
  - **"Main entry"** — `gg2d3()`.
  - **"Interactivity"** — `d3_tooltip()`, `d3_hover()`, `d3_zoom()`, `d3_brush()`, `d3_crosstalk()`.
  - **"Helpers"** (only if there are other exported symbols — planner audits `NAMESPACE`; section may collapse to a catch-all `- title: Other` if needed).
- **D-06:** Navbar uses pkgdown defaults (Home, Get started, Reference, Articles, Changelog, GitHub icon). No custom-ordered `navbar:` block.
- **D-07:** Surface `NEWS.md` as the Changelog page (pkgdown does this automatically when `NEWS.md` exists at the repo root, which it does — created in Phase 17). No News-link removal.
- **D-08:** Theme stays `template.bootstrap: 5`. No Bootswatch, no `pkgdown/extra.css`, no custom logo work in this phase.

### Articles & homepage
- **D-09:** `vignettes/gg2d3-intro.Rmd` is promoted to the navbar **"Get started"** slot (pkgdown convention — typically achieved by naming/role via the `articles:` index or a `getting-started` flag, whichever the current pkgdown release uses). `vignettes/gg2d3-interactivity.Rmd` lives under the Articles dropdown.
- **D-10:** `inst/diagnostics/d3-drawing-diagnostics.md` stays dev-only. It is **NOT** copied or referenced into `vignettes/` or `pkgdown/articles/`. Honors Phase 18 D-10 (diagnostics remains a developer-facing doc).
- **D-11:** Homepage source = `README.md`. Default pkgdown behavior (README becomes the site's `index.html`). No separate `pkgdown/index.Rmd`.
- **D-12:** Vignette chunks are **trusted as-is** — Phase 18 successfully knit them with `devtools::build_vignettes()`. The planner must include a task that runs `pkgdown::build_site()` locally during execution to verify article rendering. Intervene with chunk-option changes only on observed breakage.

### Versioning & widget rendering
- **D-13:** Single root site only. pkgdown `development: mode: release` (or absent — defaulting to release). No `/dev/` URL, no dev/release split. Appropriate for pre-CRAN 0.1.0; revisit post-1.0.
- **D-14:** **Hard requirement:** the phase is not done until at least one `gg2d3()` widget in the *published* "Get started" article is verifiably interactive — i.e., a human-checkpoint test confirms a feature like zoom, tooltip, or hover works in the browser at `https://davidzenz.github.io/gg2d3/articles/gg2d3-intro.html` (or wherever the intro lands). Build success alone is **not sufficient**.
- **D-15:** If widgets do NOT render interactively in the published site, fix in-phase — do not defer. Common fixes the planner should anticipate: ensure `htmltools::tagList()` chunk output for inline widget capture, set `screenshot.force = FALSE` in the relevant chunks, confirm `inst/htmlwidgets/lib/d3/d3.v7.min.js` is bundled into the built site under `articles/<name>_files/`, and verify pkgdown isn't stripping `<script>` tags from widget output. Plan a dedicated verification wave that runs after the local build and before the workflow is committed.

### Claude's Discretion
- Exact YAML structure of `_pkgdown.yml` (key ordering, comment style) is up to the planner as long as D-01..D-15 are honored.
- Decision of whether to keep the existing `_pkgdown.yml` stub and patch it vs. rewrite the file.
- Specific GHA workflow filename within `.github/workflows/` (`pkgdown.yaml` is conventional but `pkgdown-deploy.yaml` is acceptable).
- Whether to also add a `pkgdown/` directory with a `favicon/` subfolder (favicon work is optional; not in the locked decisions).
- How to bootstrap the initial `gh-pages` branch (manual `git checkout --orphan` once vs. letting `usethis::use_pkgdown_github_pages()` do it on first run). Planner picks one and documents in the plan.
- Exact CI matrix specs for the deferred R CMD check phase (not this phase's concern).

</decisions>

### Reusable Assets
- `_pkgdown.yml` already exists with `template.bootstrap: 5` — minimal stub to extend, not replace from scratch.
- `NEWS.md` already exists — pkgdown will pick it up automatically; no extra wiring needed.
- `vignettes/` is already populated with the two v1.1 vignettes; both build cleanly per Phase 18 (`18-build-log.txt`).
- `DESCRIPTION` is CRAN-ready (Phase 17) — `URL`, `BugReports`, `Authors@R`, `Title`, `Description` are real values, so pkgdown will populate the homepage sidebar correctly.

### Established Patterns
- README is generated from `.Rmd` via `devtools::build_readme()` (CLAUDE.md). Never hand-edit `README.md` directly — if Phase 31 changes anything README-relevant, regen from `.Rmd`.
- Vignettes are R Markdown with runnable `eval=TRUE` chunks. The d3.v7.min.js asset is loaded by htmlwidgets, not by chunk code — chunks themselves don't need pkgdown-specific overrides per D-12.
- `.Rbuildignore` is the conventional place to exclude site-build artifacts (`^docs$`, `^_pkgdown\.yml$`, `^pkgdown$`, `^\.github$`) so they don't enter the source tarball. Phase 17 already manages this file; Phase 31 must add the new entries it introduces.

### Integration Points
- The first GHA run will need a pre-existing `gh-pages` branch OR write permission for the workflow to create one. The planner must decide bootstrap approach (D-15 discretion item) and document it.
- After D-14 verification, the published site URL should be added to the GitHub repo's "About" section sidebar — not strictly in-scope for the phase plan but worth flagging in the SUMMARY.

<specifics>
## Specific Ideas

- The intro vignette already demos `gg2d3()` end-to-end; that's the natural target for the D-14 widget-interactivity human checkpoint.
- The interactivity vignette includes a Crosstalk linked-views example — verifying THAT renders correctly in the published article is a stronger end-to-end signal than zoom alone, since it exercises both htmlwidgets and the crosstalk shared-data plumbing.
- pkgdown 2.x's "Get started" promotion typically uses an `articles/` YAML section with `title: Articles` and a separate `getting-started` flag — exact syntax has shifted between minor pkgdown versions, so the researcher should pin the current pkgdown release and pull the right idiom from its docs.

</specifics>

<deferred>
## Deferred Ideas

- **R CMD check matrix on CI** — Reverted from initial D-04 selection. Belongs in its own phase (call it "Phase 20: CI hardening" or similar). Should run `r-lib/actions/check-r-package` across Ubuntu/macOS/Windows × R release/devel.
- **Custom domain (CNAME)** — e.g., `gg2d3.davidzenz.com`. Cheap to add later (CNAME file + DNS); no Phase 31 dependency.
- **PR preview deploys** — Build a temporary site per PR (e.g., via Netlify or a `pr-N` subdirectory on gh-pages). Cool, but adds CI complexity; defer to post-1.0.
- **pkgdown version pinning in the workflow** — Pin `r-lib/actions/setup-r@vX`, `pandoc` version, R version. Workflow can use r-lib defaults for now; long-term reproducibility is a fair v1.2 task.
- **Dev/release pkgdown split (`development: mode: auto`)** — Single root site is right pre-CRAN. Reconsider after first CRAN release when there will be a meaningful "released" vs "development" distinction.
- **Adding `Phase 31` REQ-IDs to `REQUIREMENTS.md`** — Phase 31 introduces publishing capability that has no current REQ-ID. The planner (or a roadmap follow-up commit) should consider adding e.g. `DOCS-02: Public package site published to GitHub Pages reflecting v1.1 docs` to `REQUIREMENTS.md` for traceability, even though it's not blocking Phase 31 execution.
- **Custom pkgdown logo / hex sticker** — Not in scope. Default pkgdown look is fine for v1.1.

</deferred>
